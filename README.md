# OpenTelemetry Distributed Tracing Lab

A hands-on distributed tracing lab using OpenTelemetry, two Python FastAPI services, Grafana Tempo, and Grafana.

The goal is to understand how traces travel across services, how distributed context is propagated, and how to investigate successful requests and application errors using trace data.

## Architecture

```text
Client
  |
  v
order-api (FastAPI :8000)
  |
  | HTTP request with trace context
  v
inventory-api (FastAPI :8001)
  |
  v
OpenTelemetry Collector
  |
  | OTLP
  v
Grafana Tempo
  |
  v
Grafana Explore
```

Both services generate trace data using OpenTelemetry instrumentation and custom spans. The Collector receives and forwards the traces to Tempo, where Grafana can query and display them.

## Components

- **Python and FastAPI:** Two small services representing an order and inventory workflow.
- **OpenTelemetry SDK and instrumentation:** Generate spans and propagate trace context across HTTP requests.
- **OpenTelemetry Collector:** Receives, processes, and exports telemetry.
- **Grafana Tempo:** Stores traces for querying.
- **Grafana:** Provides the interface for searching and exploring traces.

## Prerequisites

- Python 3.10 or later
- Docker
- Git
- Grafana
- Basic familiarity with HTTP APIs and YAML configuration

The commands below assume a Linux environment and that the services and Docker containers run on the same host. If you use separate hosts, update the endpoints and network settings accordingly.

## 1. Install Python dependencies

Clone the repository and enter the project directory:

```bash
git clone <YOUR_REPOSITORY_URL>
cd otel-order-api
```

Create and activate a virtual environment:

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

## 2. Start Grafana Tempo

Start Tempo using the configuration included in the repository:

```bash
docker run -d \
  --name tempo \
  --restart unless-stopped \
  -p 3200:3200 \
  -p 4320:4317 \
  -v "$PWD/tempo/tempo.yaml:/etc/tempo.yaml" \
  grafana/tempo:latest \
  -config.file=/etc/tempo.yaml
```

The configuration enables OTLP ingestion and local trace storage.

Check that Tempo is running:

```bash
docker logs tempo
```

Its query API should be reachable locally at `http://localhost:3200`.

## 3. Start the OpenTelemetry Collector

The Collector receives traces from the application services and forwards them to Tempo.

```bash
docker run -d \
  --name otel-collector \
  --restart unless-stopped \
  -p 4317:4317 \
  -p 4318:4318 \
  -e TEMPO_ENDPOINT=172.17.0.1:4320 \
  -v "$PWD/otel/collector-config.yaml:/etc/otelcol-contrib/config.yaml" \
  otel/opentelemetry-collector-contrib:latest \
  --config /etc/otelcol-contrib/config.yaml
```

The endpoint `172.17.0.1:4320` assumes the default Docker bridge gateway on a Linux host. If your Docker networking differs, replace it with an address reachable from the Collector container.

Check the Collector logs:

```bash
docker logs otel-collector
```

The Collector configuration in this repository uses OTLP receivers and exports traces to Tempo.

## 4. Start the application services

Open two separate terminals from the project directory.

Terminal 1 — Order API:

```bash
source venv/bin/activate
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Terminal 2 — Inventory API:

```bash
source venv/bin/activate
uvicorn inventory_api.main:app --host 0.0.0.0 --port 8001
```

Both services export traces to the local Collector using OTLP gRPC on port `4317`.

## 5. Generate sample traces

Successful request:

```bash
curl http://localhost:8000/orders/123
```

Simulated application failure:

```bash
curl http://localhost:8000/orders/500
```

Delayed request:

```bash
curl http://localhost:8000/orders/999
```

The `500` request raises an application exception. The `999` request introduces an artificial delay. These scenarios help demonstrate how errors and latency appear in traces.

## 6. Explore traces in Grafana

1. Open Grafana.
2. Add a Tempo data source if one is not already configured.
3. Set the Tempo URL to `http://localhost:3200` when Grafana and Tempo share a host and network namespace. If Grafana runs in another container or on another host, use an address reachable from Grafana.
4. Open **Explore** and select Tempo.
5. Search for traces generated by the application.
6. Open a trace to inspect the span timeline, service names, duration, attributes, and errors.

A successful order request should show spans from both `order-api` and `inventory-api` under the same distributed trace.

## What this lab demonstrates

- Creating custom spans and span attributes.
- Instrumenting FastAPI applications.
- Propagating trace context across HTTP requests.
- Using an OpenTelemetry Collector as a telemetry pipeline.
- Exporting traces to Grafana Tempo.
- Investigating application errors and delayed requests through distributed traces.

## Notes

This is a learning lab, not a production deployment. It uses local trace storage and simplified networking. Production environments require appropriate security, persistent storage, access controls, resource limits, and operational monitoring.

Configuration and software versions may need updating as upstream projects evolve.
